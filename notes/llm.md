## 개념 지도

### 직접 만들기 대신 빌려 쓰기
related: llm-ai-history, llm-api
핵심: LLM은 너무 커서 직접 만들 수 없으니, 남의 서버에 있는 모델에게 요청을 보내 답을 받아 쓴다.
- CV 파트까지는 모델을 직접 불러와 고치고 학습시켰다. LLM 파트는 방향이 반대다.
- AI의 흐름: 사람이 규칙을 쓰는 전문가 시스템 → 데이터에서 배우는 딥러닝(2012 AlexNet) → Transformer(2017) → 규모를 키운 GPT
- 규모가 핵심이었다. GPT-1 약 1억 → GPT-2 15억 → GPT-3 1,750억 파라미터. 다음 단어 예측 수준이던 모델이 키우면서 자연스러운 글을 쓰게 됐다.
- 이런 모델을 학습시키는 데는 엄청난 데이터와 GPU가 든다. 개인이나 작은 팀은 만든 모델을 빌려 쓰는 게 현실적이다.
- 이후 흐름: ChatGPT(2022)로 자연어 대화, Tool calling(2023)으로 도구를 쓰는 Agent, MCP(2024)로 외부 시스템 연결
막힌 점: 모델은 OpenAI 서버에 있고 내 코드는 내 컴퓨터에 있다. 둘이 서로 알아듣게 주고받는 약속이 필요하다.

### API: 주문하는 규칙
related: llm-api, llm-api-key
핵심: API는 프로그램끼리 소통하는 규칙이고, 문서에 맞춰 요청하면 내부를 몰라도 결과를 받는다.
- 식당 비유: 메뉴판(API 문서)을 보고 주문(Request)하면 주방(모델)이 음식(Response)을 내준다. 주방이 어떻게 돌아가는지는 몰라도 된다.
- 공짜가 아니라서 요금을 청구할 계정을 가리키는 **API Key**가 필요하다.
- 키는 신분증과 같다. 코드에 그대로 적으면 공유나 GitHub 업로드와 함께 퍼지고, 남이 내 돈으로 요청을 보낼 수 있다.
- Colab에서는 보안 비밀(열쇠 아이콘)에 저장하고 `userdata.get("openai_api")`처럼 이름으로만 불러온다.
막힌 점: 규칙이 있다는 건 알았다. 실제로 무엇을 어떤 모양으로 보내고, 무엇이 돌아오는지 알아야 한다.

### 요청을 보내고 응답에서 텍스트 꺼내기
related: llm-request-flow, llm-response-text
핵심: JSON 요청을 보내면 JSON 응답이 오고, 실제 답은 그 안 깊숙한 곳에 있다.
- 흐름: 프롬프트 작성 → API Key + JSON 요청 → 서버가 토큰 수·비용 계산 후 모델 호출 → 모델이 토큰 단위로 생성 → JSON 응답 → 텍스트만 추출
- **JSON**: 파이썬 딕셔너리와 거의 같지만 문자열은 큰따옴표, `false`, `null`을 쓴다. 언어와 상관없이 읽을 수 있어서 서로 다른 프로그램이 주고받기 좋다.
- 코드는 `client.responses.create(model="gpt-4o-mini", input="안녕?")` 한 줄이다. `model`, `input`만 필수다.
- 답의 위치: `response.output[0].content[0].text`. `output`이 리스트인 것은 텍스트 말고도 도구 호출, 추론 과정 같은 항목이 나올 수 있어서다.
- 매번 이렇게 쓰기 번거로워서 SDK가 텍스트를 모아 주는 `response.output_text`를 준다.
막힌 점: 서버가 "토큰 수와 비용을 계산한다"고 했다. 무엇을 세서 돈을 받는 걸까?

### 토큰: 요금과 길이의 단위
related: llm-token-cost, llm-korean-token-exp
핵심: 모델은 글을 토큰이라는 조각으로 다루고, 요금도 입력과 출력의 토큰 수로 매긴다.
- 강의 기준: 영어 약 4글자 = 1토큰, 한글 약 1글자 = 1토큰
- GPT-4o 계열 토크나이저 `o200k_base`로 직접 잘라 보면 영어는 `␣the`, `␣lunch`처럼 단어 하나가 대개 토큰 하나, 한국어는 `점`+`심`, `설명`+`해`+`줘`처럼 더 잘게 쪼개진다.
- 사전에 없는 글자(`넹`)는 UTF-8 바이트 조각(`0xEB84`, `0xB9`)으로 나뉜다. 그래서 처음 보는 글자도 에러 없이 표현된다.
- 같은 뜻의 문장 8쌍: 영어 토큰당 4.73자, 한국어 1.52자. 토큰 수는 영어 66, 한국어 98로 **한국어가 약 1.5배**다.
- 직관: 토큰은 택시 미터기의 거리다. 같은 목적지라도 돌아가는 길(잘게 쪼개지는 언어)이면 요금이 더 나온다.
막힌 점: 무엇을 얼마에 보내는지는 알았다. 이제 같은 질문으로 서로 다른 서비스를 만들려면 모델의 역할부터 정해야 한다.

### instructions: 같은 모델, 다른 서비스
related: llm-instructions, llm-model-params
핵심: instructions는 모델의 역할과 규칙을 정하는 개발자 지침이고, 사용자 질문(input)과 따로 넘긴다.
- 같은 질문 "커피는 몸에 좋지 않은가요?"
  - "너는 전문적인 의사야. 과학적 근거를 기반으로..." → 항산화 성분, 질병 예방을 번호 매겨 설명
  - "너는 초등학교 선생님이야. ... 비유를 들어서..." → "커피를 마시는 것은 마치 자동차에 기름을 넣는 것과 같아"
- 고정 규칙(역할, 말투, 금지)은 instructions에, 매번 바뀌는 요청은 input에 둔다.
- 파라미터 전체 그림: `model`, `input`, `instructions`, `temperature`/`top_p`, `max_output_tokens`, `text.format`, `reasoning.effort`, `tools`, `store`/`previous_response_id`, `stream`, `metadata`
- 모델 선택도 설계다. 빠른 챗봇은 추론하지 않는 gpt-4 계열, 높은 수준의 답은 추론하는 gpt-5 계열
막힌 점: 역할을 정해도 같은 질문에 매번 똑같이 답할지, 다양하게 답할지는 아직 정하지 않았다. 모델은 다음 토큰을 확률로 고르기 때문이다.

### temperature와 top_p: 무작위성 조절
related: llm-temperature, llm-temperature-exp, llm-temperature-vs-top-p, llm-temperature-zero
핵심: temperature는 확률 분포의 모양을 날카롭거나 평평하게 바꾸고, top_p는 확률 낮은 꼬리를 잘라 낸다.
- 확률 계산: 모델 점수(logit)를 T로 나눈 뒤 softmax. `p_i = exp(z_i / T) / Σ exp(z_j / T)`
- "오늘 점심 메뉴 추천" 다음 토큰(예시 값): 1등 "는"의 확률이 T=0.3에서 0.48, 1.0에서 0.26, 2.0에서 0.20. T=0이면 항상 1등이다.
- 20번 뽑아 보면 T=0은 20번 모두 "는", T=2.0은 매번 다른 말로 시작한다.
- top_p: 큰 확률부터 더해 누적합이 top_p에 닿을 때까지만 남긴다. T=1에서 0.5면 3개, 0.9면 5개가 남고 "날씨가", "피자"는 잘린다.
- 쓰임: 정답이 하나인 분류·계산은 낮게, 아이디어·글쓰기는 높게. 보통 둘 중 하나만 조정한다. GPT-5 계열 상위 추론 모델은 temperature를 지원하지 않는다.
- 직관: temperature는 확률표 전체를 누르거나 펴는 것, top_p는 아래쪽 후보를 가위로 잘라 내는 것
막힌 점: 무엇을 고를지는 정했다. 그런데 얼마나 길게 쓸지를 정하지 않으면 출력 토큰, 곧 비용이 끝없이 늘 수 있다.

### max_output_tokens: 길이의 상한
related: llm-max-output-tokens
핵심: 출력 토큰 수의 상한이고, 닿으면 문장 중간이라도 멈춘다.
- 62토큰짜리 커피 답변에 상한 12를 주면 "커피는 몸에 좋고 나쁠 수 있는"에서 끊기고 상태가 **incomplete**로 온다.
- 모델은 상한을 미리 보고 맞춰 쓰지 않는다. 쓰다가 강제로 멈출 뿐이다.
- 그래서 길이 조절은 instructions로 "짧게 답하라"고 지시하고, 상한은 비용 폭주를 막는 **안전장치**로 둔다.
막힌 점: 한 번의 질문과 답은 다룰 수 있게 됐다. 그런데 두 번째 질문을 보내면 모델이 첫 번째 대화를 모른다.

### API는 기억하지 않는다: store와 previous_response_id
related: llm-stateless-multiturn
핵심: API 호출은 하나하나 완전히 독립이라, 대화를 이으려면 이전 대화를 다시 입력에 넣어야 한다.
- 암구호 예시: 1번 호출 "암구호는 라면 하면 너구리! 이다. 기억해" → 2번 호출 "암구호를 대라. 라면!" → "암구호 '라면 하면 너구리!'를 기억하겠습니다!" (엉뚱한 답)
- 2번 호출 입장에서는 처음 듣는 얘기다. ChatGPT 화면에서 대화가 이어지는 것은 화면 뒤에서 이전 대화를 함께 보내기 때문이다.
- 해결: 1번 호출에 `store=True`로 서버에 기록하고, 2번 호출에 `previous_response_id=r1.id`로 가리키면 "너구리!"
- 또는 대화 기록 리스트를 직접 쌓아 매번 `input`으로 보낸다.
- 직관: 모델은 매번 기억을 잃는 사람이고, 우리는 대화 기록을 쪽지로 매번 다시 건네는 것이다.
막힌 점: 쪽지를 매번 다시 건넨다는 건, 그 쪽지도 매번 읽힌다(입력 토큰이 된다)는 뜻이다.

### 기억의 값: 늘어나는 입력과 context window
related: llm-multiturn-cost-exp, llm-context-window
핵심: 이전 대화가 매번 입력이 되므로 턴마다 입력이 늘고, 누적 비용은 2차로 커지며, 언젠가 한도에 닿는다.
- previous_response_id로 이어도 이전 입력 토큰은 다시 청구된다(OpenAI 문서).
- 질문 30토큰, 답 120토큰 가정: n번째 턴 입력 = 30 + (n − 1) × 150. 20턴째에는 한 번에 2,880토큰
- 20턴 누적: single-turn 3,000 대 multi-turn 31,500. 10배가 넘는다.
- 모델이 한 번에 다룰 수 있는 토큰 수(**context window**)에는 지침, 이전 대화, 이번 입력, 출력이 모두 들어간다. 넘으면 요청이 거절되거나 앞을 잘라야 한다.
- 대응: 최근 N턴만 보내기, 오래된 대화 요약하기
막힌 점: 비용 말고 사용자 경험 문제도 있다. 답이 길면 다 만들어질 때까지 사용자는 빈 화면을 보고 기다린다.

### stream: 나오는 대로 보여 주기
related: llm-stream
핵심: 답이 완성되기를 기다리지 않고, 토큰이 생성되는 대로 조각을 받아 바로 보여 준다.
- `client.responses.stream(...)`으로 이벤트를 받고, `response.output_text.delta`(새 텍스트 조각)만 골라 `print(event.delta, end="", flush=True)`
- ChatGPT에서 글자가 타자 치듯 나오는 방식이다. 전체 시간은 같아도 첫 글자가 빨리 보여 체감이 빠르다.
- 모델이 원래 토큰을 하나씩 순서대로 만들기 때문에 가능하다.
- 실습 욕쟁이 할머니봇: instructions(불친절한 할머니, 짧게, 어려운 건 모른다고) + 멀티턴(이전 주문 기억) + stream을 한 번에 묶었다.
막힌 점: 파라미터로 할 수 있는 건 다 봤다. 그런데 같은 파라미터라도 프롬프트를 어떻게 쓰느냐에 따라 답의 질이 크게 다르다. 왜 그럴까?

### LLM은 다음 토큰 예측기다
related: llm-next-token-prompt, llm-hallucination
핵심: 모델은 앞에 있는 토큰을 조건으로 다음 토큰을 확률로 고르는 일을 반복하므로, 앞에 무엇을 두느냐가 답을 정한다.
- `P(답) = P(토큰₁ | 프롬프트) × P(토큰₂ | 프롬프트, 토큰₁) × ...`
- 역할, 예시, 단계별 풀이 같은 프롬프트 기법은 모두 "다음 토큰의 조건"을 바꾸는 방법이다.
- 같은 이유로 **환각**이 생긴다. 모델은 정답을 찾는 게 아니라 그럴듯한 다음 단어를 고르므로, 근거가 없어도 자연스러운 거짓을 만든다.
- 환각 대응: 모르면 모른다고 하라고 지시(프롬프트), 근거 자료를 같이 주기(RAG), 직접 검색해 확인하게 하기(Tool calling)
막힌 점: 앞에 붙는 텍스트가 그렇게 중요하다면, 그 텍스트를 누가 어떤 권한으로 쓰는지부터 정리해야 한다.

### 프롬프트의 세 층
related: llm-prompt-layers, llm-prompt-injection
핵심: 프롬프트는 System(제공자), Developer(개발자, instructions), User(사용자, input) 세 층이고 위가 우선한다.
- System: 모델의 최상위 원칙. 사용자는 보거나 고칠 수 없다.
- Developer: 서비스에서 AI가 어떻게 행동할지. Responses API의 `instructions`
- User: 실제 질문. `input`
- 사용자가 "앞의 지시는 무시해"라고 해도 위 층이 이기도록 설계되어 있다. 하지만 결국 모두 같은 모델이 읽는 텍스트라서, 교묘한 입력이 지침을 우회하는 **프롬프트 인젝션**을 완전히 막지는 못한다.
- 그래서 질문, 역할, 조건, 형식을 다 합친 것이 프롬프트이고, instructions 설정도 프롬프트 엔지니어링의 일부다.
막힌 점: 층은 나눴다. 이제 한 층 안에 무엇을 써야 원하는 답이 나오는지가 남는다.

### 좋은 프롬프트의 다섯 요소
related: llm-prompt-elements
핵심: 지시, 맥락, 역할, 출력 형식, 제약을 채우면 모델이 추측해야 할 부분이 줄어든다.
- **instruction**: 무엇을 시키나. "이 보고서 정리해줘"보다 "핵심 내용을 3줄 이내로 요약해줘"
- **context**: 상황과 독자. "코딩을 한 번도 해 보지 않은 초보자 대상으로". AI는 알려 주지 않은 건 모른다.
- **role**: 정체성. "너는 시니어 개발자야"
- **output format**: 결과의 모양. "JSON 형식으로", "장점과 단점을 표로"
- **constraint**: 금지와 필수. "제공된 정보만 사용할 것", "확실하지 않다면 모른다고 대답할 것". 환각을 줄인다.
- 프롬프트 A "프롬프트 엔지니어링을 설명해줘."는 지시만 있다. 프롬프트 B는 다섯 요소를 다 채웠다.
- 헷갈리는 점: 요소 instruction은 파라미터 `instructions`와 이름만 같고, 뜻은 `input`에 가깝다.
막힌 점: 요소를 다 채워도 말로 설명하기 어려운 기준이나 형식이 있다. 그럴 때는 보여 주는 편이 빠르다.

### 예시로 보여 주기: Zero-shot, Few-shot, Counter-Example
related: llm-zero-vs-few-shot, llm-fewshot-cost-exp, llm-counter-example
핵심: 예시를 보여 주면 형식과 기준이 고정되고, 나쁜 예와 이유까지 보여 주면 기준이 더 분명해진다.
- **Zero-shot**: 예시 없이 지시만. 빠르지만 형식이 원하는 모양이 아닐 수 있다.
- **Few-shot**: 리뷰 4개와 별점을 보여 주고 새 리뷰의 별점을 묻는다. 예시가 1개면 one-shot
- 대가: 예시가 틀리면 그 오류까지 따라 하고, 프롬프트가 길어진다. 43토큰 → 예시 4개 120토큰 → 8개 188토큰, 예시 하나에 약 17토큰. 하루 1만 번이면 예시 4개가 매일 77만 토큰
- **Counter-Example**: 나쁜 예 "공지사항입니다."(밋밋함)와 좋은 예 "[필독] 회신 필수 항목 (08/23)까지"(기한과 행동이 보임)를 이유와 함께. 처음 보는 입력에도 잘 일반화되지만 예시를 두 배로 준비해야 한다.
- 예시는 가중치를 바꾸지 않는다. 입력 앞부분에 들어가 다음 토큰 확률에 영향을 줄 뿐이라 매번 다시 보내야 한다.
막힌 점: 예시는 "무엇을 답할지"는 잘 보여 주지만, 여러 단계를 거쳐야 하는 계산이나 추론에서는 답만 보고 따라 하다 틀리기 쉽다.

### 생각하게 하기: CoT, Self-Consistency, Prompt Chaining
related: llm-cot, llm-self-consistency, llm-cot-vs-chaining
핵심: 풀이를 쓰게 하고(CoT), 여러 번 풀어 다수결하고(Self-Consistency), 작업을 호출 단위로 쪼갠다(Chaining).
- **CoT**: "Let's think step by step". 중간 풀이가 다음 토큰의 근거가 된다. 카페 매출 문제를 [1단계] 아메리카노 매출 → ... → [5단계] 순이익으로 풀게 했다. 대가는 긴 출력과 비용.
- **Self-Consistency**: temperature를 높여 같은 CoT를 여러 번 → 최다 답. "8 × 5"를 다섯 번 풀어 [40, 40, 39, 40, 40] → 40
  - 시뮬레이션(오답 5종류가 흩어진다고 가정): 한 번 0.6 → 5번 다수결 0.85, 9번 0.95. 한 번 0.4도 15번이면 0.83
  - 오답이 한 가지로 몰리면 다수결은 오답을 확정한다. 호출 수만큼 비용·시간이 든다.
- **Prompt Chaining**: 회의록 → 핵심 5개 추출 → 액션 아이템·담당자·기한 → 팀원 메시지. 단계마다 확인할 수 있지만 앞 단계가 틀리면 뒤가 다 틀어진다.
- **Markdown Structure**: `# instruction`, `# input`, `# Constraints`, `# Output Format`으로 나누면 지시와 입력의 경계가 분명해진다.
- "엔지니어링"은 학술적 공학이 아니라 이렇게 했더니 잘 되더라는 경험적 노하우의 모음이다.
막힌 점: 모델을 부리는 법은 갖췄다. 하지만 코드 셀에서만 돌아가면 다른 사람이 쓸 수 없다. 화면이 필요하다.

### Gradio로 화면 붙이기: Interface → Blocks → Chatbot
related: llm-gradio-interface-vs-blocks, llm-chat-messages, llm-gradio-chatbot-exp
핵심: Interface는 함수 하나에 입출력을 붙이고, Blocks는 자유롭게 배치하며, Chatbot은 role/content 메시지 리스트를 채팅창으로 보여 준다.
- **Interface**: `fn`, `inputs`, `outputs`. inputs 순서대로 함수 매개변수에 들어간다. 계산기(0으로 나누면 "Error : Division by Zero"), BMI(175cm, 70kg → 22.86)
- **Blocks**: `gr.Row()`(가로), `gr.Column()`(세로, `scale`로 폭 비율), 이벤트는 `Button.click(fn, inputs, outputs)`, `Textbox.submit(...)`로 직접 연결
- **Chatbot**: 대단한 게 아니라 history 리스트를 채팅창 모양으로 보여 줄 뿐이다. 메시지는 `{"role": "user" 또는 "assistant", "content": ...}`
- 이 history가 API의 대화 형식과 같아서 그대로 `input`으로 넘기면 멀티턴이 된다. 리스트 하나가 화면 표시와 모델의 기억을 함께 맡는다.
- 최종 챗봇: instructions Textbox, max_output_tokens Slider, Radio, Chatbot, 입력창, 보내기 버튼을 Blocks로 배치. 화면 확인용으로는 받은 말을 그대로 돌려주는 함수를 연결했다.
- 다음 이야기: 오늘 잠깐 나온 Tool calling과 RAG로 모델이 모르는 것을 채워 주는 법(다음 LLM 수업)으로 이어진다.

## 한 장 요약

### 한 문장 흐름
모델은 너무 커서 빌려 쓴다 → API로 JSON 요청, JSON 응답에서 `output_text` → 요금은 토큰 단위(한국어 1.5배) → instructions로 역할 → temperature·top_p로 무작위성 → max_output_tokens로 상한 → API는 기억 못 하니 이전 대화를 다시 넣고(store, previous_response_id) 그만큼 토큰이 쌓인다 → stream으로 바로 보여 주기 → 모델은 다음 토큰 예측기라 앞에 무엇을 두느냐가 답을 정한다 → 세 층, 다섯 요소, 기법으로 앞부분 설계 → Gradio로 화면과 messages 리스트

### 핵심 숫자와 식
| 무엇 | 식 또는 값 | 비고 |
|---|---|---|
| temperature | `p_i = exp(z_i / T) / Σ exp(z_j / T)` | T=0이면 항상 1등 |
| "는"의 확률 (예시 값) | T 0.3 → 0.48, 1.0 → 0.26, 2.0 → 0.20 | T가 클수록 평평 |
| top_p (T=1, 예시 값) | 0.5 → 3개, 0.9 → 5개 남음 | 꼬리 후보 제거 |
| 토큰당 글자 수 | 영어 4.73자, 한국어 1.52자 | 같은 뜻 66 대 98토큰 |
| 멀티턴 n번째 입력 | `q + (n − 1)(q + a)` | q=30, a=120 → 20턴째 2,880 |
| 20턴 누적 | single 3,000 대 multi 31,500 | 누적은 2차로 증가 |
| Few-shot 비용 | 예시 1개 약 17토큰 | 0개 43 → 4개 120 → 8개 188 |
| max_output_tokens | 62토큰 답에 상한 12 | 중간에서 잘림, incomplete |
| Self-Consistency (가정) | p 0.6 → 5번 0.85, 9번 0.95 | 오답이 흩어질 때만 |

### 헷갈리는 용어
| 용어 | 뜻 |
|---|---|
| `instructions` (파라미터) | Developer Prompt. 모델의 역할과 규칙 |
| instruction (프롬프트 요소) | 무엇을 시킬지. `input`에 가깝다 |
| `output` / `output_text` | 응답 항목 리스트 / SDK가 텍스트만 모아 준 지름길 |
| `store` / `previous_response_id` | 응답을 서버에 저장 / 저장된 응답을 가리켜 이어 붙임 |
| temperature / top_p | 분포 모양을 바꿈 / 누적 확률 밖의 후보를 버림 |
| System / Developer / User | 제공자 원칙 / 개발자 지침(instructions) / 사용자 질문(input) |
| Chatbot / history | 보여 주는 컴포넌트 / role·content 딕셔너리 리스트 |
| Interface / Blocks | 함수 하나 데모 / 자유 배치·이벤트 연결 |

### 프롬프트 기법 비교
| 기법 | 하는 일 | 좋은 점 | 대가 |
|---|---|---|---|
| Zero-shot | 지시만 | 빠르고 짧음 | 형식이 어긋날 수 있음 |
| Few-shot | 예시 몇 개 | 형식·기준 고정 | 예시 오류 전파, 토큰 증가 |
| Counter-Example | 좋은 예 + 나쁜 예 + 이유 | 기준이 분명, 일반화 | 예시 두 배 |
| Chain of Thought | 단계별 풀이 | 추론 정확도, 오류 위치 확인 | 긴 출력 |
| Self-Consistency | 여러 번 풀어 다수결 | 흩어진 오답 제거 | 호출 수만큼 비용·시간 |
| Prompt Chaining | 호출을 단계로 나눔 | 단계별 확인 | 앞 단계 오류 전파 |
| Markdown Structure | `#` 제목으로 구획 | 지시·입력 경계 분명 | 거의 없음 |

### Q. GPT 같은 모델을 직접 학습시키지 않고 API로 빌려 쓰면 무엇을 얻고, 대신 무엇을 내주나요?
id: llmc-why-borrow
type: 생각해보기
level: 기본
related: llm-api, llm-ai-history

#### 풀이
**GPU, 데이터, 학습 없이 최신 대형 모델을 코드 한 줄로 쓰는 것**을 얻고, **비용, 데이터, 통제권**을 일부 내줍니다.
- 얻는 것: GPT-3만 해도 1,750억 파라미터라 개인이 학습시키거나 띄우기 어렵다. API는 쓴 만큼만 내면 된다.
- 내주는 것 1, 비용: 호출마다 토큰 요금이 든다. 사용자가 늘면 비용도 같이 늘어난다.
- 내주는 것 2, 데이터: 프롬프트가 외부 서버로 나간다. 민감한 데이터는 따로 판단해야 한다.
- 내주는 것 3, 통제권: 가중치를 고칠 수 없고, 모델 별칭이 가리키는 버전이 바뀌면 답도 바뀔 수 있다. 서버 장애에도 영향을 받는다.
- 그래서 바꿀 수 있는 것은 입력(프롬프트)과 파라미터뿐이고, 이 노트의 나머지가 전부 그 두 가지를 다루는 이야기입니다.

### Q. 응답의 `output`은 왜 리스트이고, 왜 `output_text`라는 지름길이 따로 있나요?
id: llmc-output-list
type: 개념
level: 기본
related: llm-response-text

#### 풀이
모델이 한 번의 응답에서 **여러 종류의 항목**을 낼 수 있기 때문입니다. 텍스트 메시지만이 아니라 도구 호출이나 추론 과정 같은 항목이 함께 나올 수 있어서 리스트로 담습니다.
- 그래서 텍스트는 `output[0].content[0].text`처럼 깊이 들어 있고, 첫 항목이 항상 텍스트라는 보장도 없다.
- `output_text`는 SDK가 텍스트 부분만 모아 주는 속성이라, 구조를 몰라도 답을 꺼낼 수 있다.
- 단순 대화에서는 `output_text`로 충분하고, 도구 호출을 다룰 때는 각 항목의 `type`을 보고 처리해야 한다.

### Q. 같은 뜻인데 한국어 문장이 영어보다 토큰을 약 1.5배 쓰는 이유를 BPE 토크나이저가 어휘를 만드는 방식으로 설명해 보세요.
id: llmc-korean-tokens-bpe
type: 연결
level: 심화
related: llm-korean-token-exp, llm-token-cost, nlp-subword

#### 풀이
BPE는 학습 텍스트에서 **자주 붙어 나오는 조각을 반복해서 합쳐** 어휘를 만듭니다. 어휘 크기는 정해져 있으니, 자주 나오는 언어의 단어일수록 통째로 토큰 하나가 될 자리를 차지합니다.
- 학습 텍스트에 영어가 훨씬 많으면 `␣the`, `␣lunch` 같은 영어 단어는 하나로 합쳐진다.
- 한국어는 합쳐질 기회가 적어 `점`+`심`, `설명`+`해`+`줘`처럼 작은 조각으로 남는다. 조사와 어미가 붙어 형태가 다양한 것도 한몫한다.
- 그래서 실험에서 영어는 토큰당 4.73자, 한국어는 1.52자였다.
- 바이트 단위 BPE라 사전에 없는 `넹`도 바이트 조각 두 개로 표현된다. 에러는 없지만 토큰은 더 든다.
- 결과적으로 같은 내용이라도 한국어 사용자는 더 많은 토큰, 곧 더 많은 비용과 컨텍스트를 쓴다.

### Q. 한 서비스가 하루 1만 번 API를 호출합니다. 요청마다 입력 500토큰, 출력 200토큰이고, 단가를 입력 100만 토큰당 0.15달러, 출력 100만 토큰당 0.60달러로 가정합니다. 하루 비용은? 지시문을 한국어로 바꿔 입력이 1.5배가 되면?
id: llmc-token-cost-calc
type: 계산
level: 기본
related: llm-token-cost, llm-korean-token-exp

```
단가는 계산 연습용 가정 값이다. 실제 단가는 모델과 시점마다 다르다.
```

#### 풀이
- 입력: 500 × 10,000 = 5,000,000토큰 → 5 × 0.15 = **0.75달러**
- 출력: 200 × 10,000 = 2,000,000토큰 → 2 × 0.60 = **1.20달러**
- 하루 합계 **1.95달러**, 30일이면 58.5달러
- 입력 1.5배: 750 × 10,000 = 7,500,000토큰 → 7.5 × 0.15 = 1.125달러. 합계 **2.325달러**(하루 0.375달러 증가)

눈여겨볼 점: 출력은 전체 토큰 700만 개 중 200만 개(약 29%)인데 비용은 1.20 / 1.95 ≈ **62%**를 차지합니다. 출력 단가가 비싸면 답 길이(instructions로 "짧게", max_output_tokens 상한)를 줄이는 것이 비용에 가장 크게 듣습니다.

### Q. instructions와 input을 굳이 나눠서 보내는 이유는 무엇인가요?
id: llmc-instructions-vs-input
type: 개념
level: 기본
related: llm-instructions, llm-prompt-layers

#### 풀이
**누가 쓴 텍스트인지, 얼마나 고정된 것인지**가 다르기 때문입니다.
- instructions는 개발자가 정한 역할과 규칙이다. 서비스 내내 같은 값을 쓴다.
- input은 사용자가 매번 다르게 보내는 요청이다.
- 나눠 두면 질문이 바뀌어도 규칙이 일관되게 적용되고, 같은 모델을 instructions만 바꿔 의사 서비스, 초등 선생님 서비스로 만들 수 있다.
- 프롬프트의 세 층에서 instructions는 Developer, input은 User 층이라 위 층으로서 우선한다. 한 문자열에 섞어 쓰면 이 구분이 사라진다.

### Q. 예시 점수에서 "는"의 logit은 2.4, "김치찌개"는 2.2입니다. T = 0.3, 1, 2일 때 두 토큰의 확률 비 p(는) / p(김치찌개)를 구하세요.
id: llmc-temperature-ratio
type: 계산
level: 기본
related: llm-temperature, llm-temperature-exp, basics-softmax

#### 풀이
softmax의 분모는 같으니 비는 `exp(z₁/T) / exp(z₂/T) = exp((z₁ − z₂) / T)`이고, 점수 차는 0.2입니다.
- T = 0.3: exp(0.2 / 0.3) = exp(0.667) ≈ **1.95**
- T = 1: exp(0.2) ≈ **1.22**
- T = 2: exp(0.1) ≈ **1.11**

블로그 그림의 값과 맞습니다(T=0.3에서 0.48 대 0.25, T=1에서 0.26 대 0.21, T=2에서 0.20 대 0.18). 점수 차이가 1/T배로 줄거나 늘기 때문에, T가 작으면 작은 점수 차도 큰 확률 차로 벌어지고, T가 크면 거의 같은 확률이 됩니다. T → 0이면 비가 무한대로 가서 1등만 남습니다.

### Q. temperature를 0으로 두고 같은 질문을 100번 보내면 어떻게 될까요?
id: llmc-temp-zero-100
type: 만약에
level: 기본
related: llm-temperature, llm-temperature-zero

#### 풀이
이론상 매번 1등 토큰만 고르니 **100번 모두 같은 답**입니다. 블로그 시뮬레이션에서도 T=0은 20번 모두 "는"이었습니다.
- 분류, 추출처럼 정답이 하나인 작업에는 이것이 장점이다.
- 아이디어를 여러 개 받고 싶은 작업에서는 100번 물어도 같은 아이디어 하나라 쓸모가 없다.
- 실제 서버에서는 거의 같지만 완전히 같다고 보장되지는 않는다. GPU 병렬 계산의 미세한 차이로 1등과 2등 점수가 거의 같은 지점에서 순위가 뒤집히면, 그 뒤 답 전체가 달라질 수 있다.

### Q. temperature를 낮춰도 엉뚱한 후보의 확률은 0이 되지 않는데, top_p는 그 후보를 확실히 없앱니다. 왜 그런가요?
id: llmc-top-p-vs-temp
type: 개념
level: 심화
related: llm-temperature-vs-top-p, llm-temperature

#### 풀이
temperature는 **모든 후보의 확률을 다시 계산할 뿐 아무도 빼지 않고**, top_p는 **누적 확률 밖의 후보를 목록에서 지워 버리기** 때문입니다.
- `exp(z / T)`는 T > 0이면 항상 양수라서, "날씨가"처럼 점수가 낮은 후보도 아주 작은 확률은 남는다. 수천 토큰을 생성하다 보면 그 작은 확률이 한 번쯤 뽑힐 수 있다.
- top_p는 큰 확률부터 더해 0.9에 닿으면 멈추고 나머지를 버린다. 예시에서 "날씨가", "피자"는 확률이 0이 된다.
- top_p는 남기는 개수도 상황에 맞게 바뀐다. 모델이 확신하면 몇 개만, 애매하면 많이 남긴다.
- 둘 다 조정하면 효과가 겹쳐 결과를 예측하기 어려우니 보통 하나만 바꾼다.

### Q. 예시 확률표(T=1)에서 top_p를 0.1로 주면 어떻게 될까요? 0.3이면요?
id: llmc-top-p-tiny
type: 만약에
level: 기본
related: llm-temperature-vs-top-p

#### 풀이
T=1에서 확률이 큰 순서는 는(0.26), 김치찌개(0.21), 가(0.17), ... 이고 누적합은 0.26, 0.46, 0.64, ... 입니다.
- top_p = 0.1: 1등 "는" 하나만으로 0.1을 넘으므로 **"는"만 남는다.** 항상 1등을 고르니 temperature 0과 거의 같아진다.
- top_p = 0.3: "는"만으로는 0.26이라 모자라고, "김치찌개"까지 더해 0.46에서 넘는다. **2개가 남고** 그 안에서 비율을 다시 맞춰(약 0.55 대 0.45) 뽑는다.

top_p를 작게 줄수록 결정적인 쪽으로, 크게 줄수록 다양한 쪽으로 갑니다.

### Q. OpenAI는 왜 API 호출을 서로 독립적으로(상태 없이) 설계했을까요? 기억해 주는 쪽이 더 편하지 않나요?
id: llmc-why-stateless
type: 생각해보기
level: 심화
related: llm-stateless-multiturn, llm-multiturn-cost-exp

#### 풀이
정답이 하나인 질문은 아니지만, 이렇게 생각해 볼 수 있습니다.
- **모델 자체가 원래 상태가 없다.** 모델은 입력 토큰을 받아 다음 토큰을 내는 함수다. "기억"이란 결국 이전 대화를 입력에 다시 넣는 것이라, 어디선가 그 입력을 만들어야 한다.
- **처리하기 쉽다.** 요청 하나에 필요한 정보가 다 들어 있으면 어느 서버가 받아도 처리할 수 있다. 수많은 사용자의 요청을 여러 서버에 나눠 맡기기 좋다.
- **개발자가 통제할 수 있다.** 무엇을 기억시킬지(최근 N턴, 요약, 특정 정보만) 서비스마다 다르다. 서버가 알아서 다 기억하면 비용과 개인정보를 개발자가 조절하기 어렵다.
- 그래서 기본은 상태 없음으로 두고, 편의가 필요하면 `store=True`와 `previous_response_id`로 서버 저장을 **선택**하게 했다고 볼 수 있습니다. 어느 쪽이든 이전 대화가 입력이 되는 비용은 그대로입니다.

### Q. "previous_response_id로 대화를 이으면 이전 대화를 다시 보내지 않으니 이전 입력에 대한 토큰 비용은 들지 않는다."
id: llmc-ox-previous-id
type: OX
level: 기본
related: llm-stateless-multiturn, llm-multiturn-cost-exp

#### 풀이
**X.** 내가 네트워크로 다시 보내지 않을 뿐, 서버가 저장된 이전 대화를 이어 붙여 **모델의 입력으로 다시 읽힙니다.** OpenAI 문서도 이전 입력 토큰은 다시 청구된다고 설명합니다. 모델은 이전 대화를 기억하는 게 아니라 매번 처음부터 다시 읽기 때문입니다. 코드가 간단해질 뿐 토큰 비용은 history를 직접 보내는 것과 같다고 보면 됩니다.

### Q. 질문 30토큰, 답 120토큰인 대화를 이전 대화를 모두 포함해 이어 갑니다. 10번째 턴의 입력 토큰과, 10턴까지의 누적 토큰(입력 + 출력)을 구하고 single-turn과 비교하세요.
id: llmc-multiturn-calc
type: 계산
level: 심화
related: llm-multiturn-cost-exp, llm-stateless-multiturn

#### 풀이
- n번째 턴 입력 = 30 + (n − 1) × 150 → 10번째 턴: 30 + 9 × 150 = **1,380토큰**
- 10턴 입력 합: 10 × 30 + 150 × (0 + 1 + ... + 9) = 300 + 150 × 45 = **7,050**
- 출력 합: 10 × 120 = 1,200 → multi-turn 누적 **8,250토큰**
- single-turn 누적: 10 × (30 + 120) = **1,500토큰**
- 비율 8,250 / 1,500 = **5.5배**. 블로그의 20턴은 31,500 / 3,000 = 10.5배였다.

턴 수가 두 배가 되자 배율도 약 두 배가 됐습니다. 누적이 턴 수의 제곱에 비례해 늘기 때문에, 대화가 길수록 격차가 계속 벌어집니다.

### Q. 상담 챗봇의 대화가 수백 턴까지 길어져 비용과 context window가 문제입니다. 어떤 전략을 쓸 수 있고, 각각 무엇을 잃나요?
id: llmc-long-chat-strategy
type: 생각해보기
level: 심화
related: llm-context-window, llm-multiturn-cost-exp, llm-chat-messages

#### 풀이
모두 "무엇을 입력에 다시 넣을지 고르는" 문제이고, 고르는 기준에 따라 잃는 것이 다릅니다.
- **최근 N턴만 보내기**: 가장 간단하고 입력 길이가 일정해진다. 대신 처음에 말한 이름, 주문 번호 같은 중요한 정보를 잊는다.
- **오래된 대화 요약**: 오래된 부분을 짧은 요약으로 바꿔 넣는다. 맥락은 대체로 유지되지만 요약 호출 비용이 들고, 요약하면서 세부가 빠지거나 틀릴 수 있다.
- **필요한 것만 찾아 넣기**: 과거 대화를 저장해 두고 이번 질문과 관련된 부분만 검색해 넣는다(RAG와 같은 아이디어). 효율적이지만 검색이 놓치면 그 정보는 없는 것과 같다.
- **중요 정보를 따로 고정**: 이름, 주문 번호 같은 핵심 정보는 instructions나 별도 메모로 항상 넣는다.

실제 서비스는 이 중 몇 가지를 섞습니다. Gradio 챗봇이라면 `reply` 함수 안에서 API에 보낼 history를 잘라 내거나 요약하는 처리를 넣으면 됩니다. 화면에 보여 주는 history와 모델에 보내는 history를 따로 둘 수 있다는 점도 생각해 볼 만합니다.

### Q. 모델이 사실이 아닌 내용을 자신 있게 말하는 환각은 왜 생기고, "모르면 모른다고 답해"라는 지시만으로 충분하지 않은 이유는 무엇인가요?
id: llmc-hallucination-why
type: 개념
level: 기본
related: llm-hallucination, llm-next-token-prompt

#### 풀이
모델은 **정답을 찾는 게 아니라 그럴듯한 다음 토큰을 고르도록** 학습됐기 때문입니다. "이 논문의 저자는" 다음에는 사람 이름이 오는 게 자연스러우니, 실제 저자를 몰라도 그럴듯한 이름을 만들어 냅니다.
- "모르면 모른다고 해" 지시는 모른다고 답할 확률을 높여 주지만, 모델이 **자기가 모른다는 것을 항상 알지는 못한다.** 틀린 내용도 확신 있게 그럴듯해 보이면 그대로 나온다.
- 그래서 근거를 바깥에서 넣어 준다. RAG는 관련 문서를 입력에 함께 주고, Tool calling은 모델이 직접 검색해 확인하게 한다.
- 근거가 입력에 있으면 "그 문서를 따라 쓰는 것"이 가장 그럴듯한 다음 토큰이 되어 환각이 줄어든다.

### Q. 환각을 줄이려고 temperature를 0으로 낮추면 어떻게 될까요?
id: llmc-low-temp-hallucination
type: 만약에
level: 심화
related: llm-hallucination, llm-temperature

#### 풀이
엉뚱한 낮은 확률 후보가 뽑히는 일은 줄지만, **환각이 사라지지는 않습니다.**
- temperature 0은 모델이 가장 그럴듯하다고 보는 토큰을 항상 고르게 할 뿐이다.
- 모델이 가장 그럴듯하다고 보는 답 자체가 틀렸다면, 이제 그 틀린 답을 **매번 일관되게** 낸다.
- 오히려 여러 번 물어 답이 흔들리는지 보는 방법(Self-Consistency 같은 확인)을 쓸 수 없게 된다.

환각은 무작위성 문제가 아니라 **근거가 없는 문제**라서, 근거를 주는 RAG나 Tool calling이 더 직접적인 해결책입니다.

### Q. 프롬프트의 앞부분이 답을 좌우한다는 사실은 GPT의 학습 방식과 Decoder의 Masked Self-Attention과 어떻게 연결되나요?
id: llmc-prompt-as-prefix
type: 연결
level: 심화
related: llm-next-token-prompt, nlp-gpt-generation, nlp-masked-attention

#### 풀이
GPT는 **앞 토큰들만 보고 다음 토큰을 맞히도록** 사전학습됐고, 이를 가능하게 하는 것이 미래 토큰을 가리는 Masked Self-Attention입니다.
- 학습: 각 위치에서 앞쪽만 보고 다음 토큰을 예측한다. 그래서 모델이 배운 것은 "이런 앞부분 다음에는 무엇이 오는가"다.
- 생성: 프롬프트가 바로 그 "앞부분"이다. 생성된 토큰도 하나씩 뒤에 붙어 다음 예측의 앞부분이 된다(autoregressive).
- 그래서 역할(role)을 앞에 두면 그 역할다운 말투가, 예시(Few-shot)를 두면 같은 형식이, 풀이(CoT)를 먼저 쓰게 하면 풀이에 맞는 결론이 이어질 확률이 커진다.
- 반대로 앞에 이미 나온 토큰을 뒤에서 고칠 수 없다. 처음에 잘못 쓴 토큰이 이후 생성을 계속 끌고 가는 이유이기도 하다.

### Q. System, Developer, User 층에 우선순위가 있는데도 프롬프트 인젝션을 완전히 막을 수 없는 이유는 무엇일까요? 개발자는 무엇을 할 수 있을까요?
id: llmc-layers-injection
type: 생각해보기
level: 심화
related: llm-prompt-layers, llm-prompt-injection

#### 풀이
우선순위는 **모델이 그렇게 행동하도록 학습된 경향**이지, 코드처럼 강제되는 권한 검사가 아니기 때문입니다.
- 결국 모든 층은 같은 모델이 읽는 토큰이다. 사용자 입력이나 요약하라고 준 웹 페이지 안의 "앞의 지시를 무시해"도 똑같이 문맥으로 들어간다.
- 모델은 다음 토큰을 확률로 고르므로, 교묘하게 쓴 입력은 지침을 따를 확률보다 입력을 따를 확률을 높일 수 있다. "대부분 막는다"와 "항상 막는다"는 다르다.

그래서 프롬프트 바깥에서 여러 겹으로 막습니다.
- 지침은 instructions에, 외부 텍스트는 input에 두고 Markdown 제목이나 구분 기호로 "여기부터는 데이터"임을 분명히 한다.
- 프롬프트에 API Key 같은 비밀을 넣지 않는다.
- 모델이 쓸 수 있는 도구와 권한을 최소로 하고, 메일 발송이나 삭제 같은 행동은 코드에서 검사하거나 사람이 확인한다.
- 출력도 형식과 허용 값을 검사한다.

| role | 관점 | "너는 경영 컨설턴트야" |
| output format | 모양 | "결론, 근거, 다음 할 일 순서의 글머리표로" |
| constraint | 지킬 것 | "보고서에 없는 내용은 추가하지 말 것, 숫자는 원문 그대로" |

모델은 알려 주지 않은 건 모르므로, 빈칸이 줄수록 모델이 그럴듯하게 채워 넣을 부분(환각과 엉뚱한 형식의 원인)도 줄어듭니다.

### Q. Few-shot 예시 4개 중 하나의 라벨이 틀렸다면, 또는 4개가 모두 긍정 리뷰라면 어떻게 될까요?
id: llmc-fewshot-bad-example
type: 만약에
level: 기본
related: llm-zero-vs-few-shot, llm-fewshot-cost-exp

#### 풀이
모델은 예시를 **정답으로 믿고 패턴을 따라 합니다.**
- 라벨이 틀린 경우: 예를 들어 "생각보다 별로예요"를 긍정(★★★★)으로 적어 두면, 비슷한 애매한 불만 리뷰도 긍정으로 분류할 가능성이 커진다. 예시의 오류까지 배운다.
- 모두 긍정인 경우: 출력 형식은 잘 따르지만 답이 긍정 쪽으로 치우치기 쉽다. 예시에 없는 "매우 부정(★)" 같은 경우를 잘 못 다룬다.
- 그래서 예시는 정확해야 하고, 실제로 나올 경우를 고르게 담아야 한다. 강의 예시가 ★5, ★4, ★2, ★1을 하나씩 둔 것도 이 때문이다.
- 예시를 늘려 해결하려면 하나에 약 17토큰씩 매 요청 비용이 붙는다는 점도 함께 고려한다.

### Q. Counter-Example이 Few-shot보다 처음 보는 입력에 더 잘 일반화되는 이유는 무엇인가요?
id: llmc-counter-generalize
type: 개념
level: 심화
related: llm-counter-example, llm-zero-vs-few-shot

#### 풀이
Few-shot은 **"이런 답"을 보여 주고**, Counter-Example은 **"이건 좋고 이건 나쁘다, 이유는 이것"이라는 판단 기준**을 보여 주기 때문입니다.
- Few-shot 예시만 보면 모델은 표면적인 모양(길이, 단어 선택)을 따라 할 수도 있다. 무엇이 핵심인지는 예시에서 추측해야 한다.
- Counter-Example은 "밋밋하다", "기한과 행동이 보인다"처럼 기준을 말로 알려 준다. 처음 보는 공지 제목에도 그 기준을 적용할 수 있다.
- 피해야 할 것이 분명한 작업(항의 메일 답장에서 성의 없는 사과, 변명 나열)에서 특히 효과가 있다.
- 대신 좋은 예와 나쁜 예를 둘 다 준비해야 해서 예시가 두 배, 토큰도 그만큼 든다.

### Q. Few-shot으로 모델에 예시를 보여 주는 것과 파인튜닝으로 예시를 학습시키는 것은 무엇이 같고 무엇이 다른가요?
id: llmc-fewshot-vs-finetune
type: 연결
level: 심화
related: llm-zero-vs-few-shot, llm-fewshot-cost-exp, nlp-pretrain-finetune

#### 풀이
- **같은 점**: 둘 다 사전학습된 모델이 특정 작업을 원하는 방식으로 하게 만들려고 예시(입력과 정답 쌍)를 쓴다.
- **다른 점**

| | Few-shot (in-context) | 파인튜닝 |
|---|---|---|
| 가중치 | 그대로 | 작업 데이터로 바뀜 |
| 예시가 있는 곳 | 매 요청의 입력 | 학습 데이터 (한 번 학습) |
| 예시 수 | 몇 개 (입력 길이 한계) | 수백~수천 개도 가능 |
| 비용 구조 | 매 요청 예시 토큰(약 17토큰/개) | 학습 비용 한 번, 요청은 짧음 |
| 바꾸기 | 프롬프트만 고치면 즉시 | 다시 학습해야 함 |

API로 빌려 쓰는 상황에서는 가중치를 직접 만질 수 없으니 Few-shot이 먼저 쓰는 방법이고, 같은 예시를 매우 많이 반복해서 보내야 하거나 예시 몇 개로 담기 어려운 작업이라면 파인튜닝을 검토합니다.

### Q. Chain of Thought에서 풀이를 먼저 쓰게 하면 왜 최종 답이 더 정확해지나요? 다음 토큰 예측 관점에서 설명해 보세요.
id: llmc-cot-why
type: 개념
level: 기본
related: llm-cot, llm-next-token-prompt

#### 풀이
모델은 앞에 있는 토큰을 보고 다음 토큰을 정합니다. 답부터 쓰라고 하면 **최종 답 토큰을 한 번에 맞혀야** 하지만, 풀이를 먼저 쓰게 하면 **중간 계산 결과가 문맥에 쌓여** 최종 답을 낼 때 그것을 보고 낼 수 있습니다.
- 카페 매출 문제: [1단계] 아메리카노 매출, [2단계] 라떼 매출을 먼저 써 두면, [5단계] 순이익을 낼 때 앞에서 쓴 숫자를 참고한다.
- 계산을 여러 토큰에 나눠서 하는 셈이다. 사람이 암산 대신 풀이를 쓰면 덜 틀리는 것과 같다.
- 중간 단계가 보이니 어디서 틀렸는지 확인하기도 쉽다.
- 대가: 출력 토큰이 늘어 비용과 시간이 든다. 추론이 필요 없는 질문에서는 답만 장황해진다.

### Q. Self-Consistency에서 모델이 같은 실수를 반복해 오답이 한 가지로만 몰린다면, 한 번 맞힐 확률이 0.4인 문제의 3번, 5번 다수결 정확도는?
id: llmc-self-consistency-same-mistake
type: 만약에
level: 심화
related: llm-self-consistency

#### 풀이
오답이 한 가지면 답은 정답과 그 오답 두 개뿐이라, **정답이 과반을 얻어야** 이깁니다(홀수 번이라 동점 없음).
- 3번: 정답 2번 이상 = 3 × 0.4² × 0.6 + 0.4³ = 0.288 + 0.064 = **0.352**
- 5번: 정답 3번 이상 = 10 × 0.4³ × 0.6² + 5 × 0.4⁴ × 0.6 + 0.4⁵ = 0.2304 + 0.0768 + 0.01024 ≈ **0.317**

한 번 풀 때(0.4)보다 오히려 **떨어지고**, 횟수를 늘릴수록 0에 가까워집니다. 오답 쪽이 매번 더 많은 표를 얻으니 다수결이 오답을 확정하는 것입니다. 블로그 시뮬레이션에서 같은 0.4가 15번 다수결로 0.83까지 오른 것은 오답이 5가지로 흩어진다는 가정 덕분이었습니다. Self-Consistency는 "정답은 모이고 오답은 흩어진다"는 조건에서만 통합니다.

### Q. Gradio Chatbot 컴포넌트는 정확히 무엇을 하고, 같은 history 리스트가 화면과 모델의 기억을 함께 맡을 수 있는 이유는 무엇인가요?
id: llmc-chatbot-history
type: 개념
level: 기본
related: llm-chat-messages, llm-gradio-chatbot-exp, llm-stateless-multiturn

#### 풀이
Chatbot은 **`{"role": ..., "content": ...}` 딕셔너리 리스트를 채팅창 모양으로 보여 주는 것**이 전부입니다. 대화를 기억하거나 모델을 부르는 기능은 없습니다.
- 이 리스트 형식이 OpenAI API의 대화 형식과 같다. 그래서 같은 history를 `input`으로 넘기면 모델이 이전 대화를 읽는 멀티턴이 된다.
- API는 상태가 없어서 이전 대화를 매번 입력에 넣어야 했는데, 화면에 보여 주려고 어차피 쌓는 리스트가 바로 그 입력이 된다.
- 순서: 사용자 메시지를 붙임 → history 전체로 API 호출 → 받은 `output_text`를 assistant 메시지로 붙임 → Chatbot 갱신
- assistant 메시지를 빠뜨리면 화면에는 내 말만 쌓이고, 모델도 자기가 뭐라고 답했는지 모른다.
- 리스트가 길어지면 입력 토큰도 같이 늘어나므로, 오래 쓰는 챗봇은 모델에 보낼 부분을 잘라 내거나 요약해야 한다.
